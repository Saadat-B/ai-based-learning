Recommended order

Interview value per hour first, prerequisites respected, and never more than one main tier, one side track and DSA at the same time. Track D (DSA) runs underneath everything, a few problems every week, from day one.

  1. Foundations

    Tier 1, with Track Q phases Q1–Q3 alongside. Then Track F, testing out of what you already know.

  2. The core product

    Track E, then Tier 2, with Track N and Track Q phases Q4–Q8 alongside. Then Track O phases O1–O3, to deploy the shop properly.

  3. AI

    Tier 3 with Track L alongside, then Tier 4 with Track P alongside. Track S drills start here, one every week or two from now on.

  4. Checkpoint: interview-ready

    Full-stack, backend and AI-engineering roles. Start applying here rather than waiting.

  5. Agentic engineering and security

    Track A, with Track X phases X1–X3 alongside, while the agent and AI security work from Tiers 3–4 is fresh.

  6. Distributed systems

    Tier 5 with Track O phases O4–O5 alongside, then Tier 6 with Track B alongside. Targeting fintech? Do the wallet and ledger phase as soon as Tier 2 is done.

  7. Scale and infrastructure

    Tier 7, with Track X phases X4–X7 alongside. Then Track O phases O6–O7, and then Track J (banks, insurers, enterprises) or Track G (infrastructure, high-scale product companies).

  8. Checkpoint: senior backend ready

    Everything after this adds depth without delaying when you can apply.

  9. Depth

    Tier 8 (needs Track P, and serves models on your Tier 7 setup), then Tier 9, Tier 10, and the remaining language track.

The loop for every stage

Each stage is small: one idea, usually under 150 lines of new code. You don’t start the next one until the quiz says you own this one.

  1. Brief

    Claude restates the goal, lists the files it will touch, and asks you one design question. You answer before any code is written.

  2. Build small

    Claude implements only this stage. No future features, no extra dependencies without asking.

  3. Walk through

    Claude explains the code file by file, focused on why, and points out the lines worth studying closely.

  4. Predict, then run

    You say what will happen, then it runs. A wrong prediction is the most useful thing that can happen here.

  5. Break it

    You try the stage’s break-it experiments and diagnose them yourself first. Hints only if you ask.

  6. Quiz gate

    4–6 questions, one at a time, graded solid, partial or missing. Anything below solid gets explained and re-asked.

  7. Log

    Claude adds an entry to learning/LOG.md: what was built, decisions, what broke, gaps, and one interview line.

  8. Commit and clear

    Commit the stage, run /clear, and start the next one with /next. Progress lives in files, not in chat history.

Set up Claude Code

Claude Code reads CLAUDE.md at the start of every session, so that file turns it into a tutor that follows the loop. Custom commands in .claude/commands/ give you shortcuts like /next and /quiz.

  1. Create a folder called task-api and run git init.
  2. Add the files below at the paths shown. Copy each one with its button.
  3. Run claude in the folder and type /next. It will start with the brief for stage 1.1.
  4. After each passed quiz, commit with a message like stage 1.1: skeleton.
  5. Run /clear before the next stage so the context stays focused.
  6. At the end of a phase, run /milestone 1 (or 2, or 3).
  7. Every few stages, run /review to get asked about older stages again.
  8. Side tracks run in their own folders. Set each one up the same way when its start point comes, and use /mock dsa, /mock lld, /mock design or /mock sql for timed mock interviews.
Use plan mode (Shift+Tab in Claude Code) for the brief step if you want to see the plan before any file is touched.

## State files
- learning/ROADMAP.md: every stage, its goal, break-it ideas and quiz focus
- learning/PROGRESS.md: current stage and its status
- learning/LOG.md: one entry per finished stage, including quiz gaps

Read all three at the start of every session.

## The stage loop
1. Brief: restate the stage goal in 2-3 lines, list the files you will
   touch, and ask me one design question (for example which status code,
   which column type, where a check belongs). Wait for my answer.
2. Build: implement only this stage. Keep the diff small (aim under ~150
   lines). No code that belongs to a later stage.
3. Walk through: explain what you wrote, file by file, focused on why.
   Point out the 1-2 lines I should study most closely.
4. Predict, then run: before running anything, ask me what I expect.
   Then run it and compare with my prediction.
5. Break it: give me the stage's break-it experiments one at a time.
   Let me diagnose first. Give hints only when I ask.
6. Quiz gate: ask 4-6 questions, ONE AT A TIME, and wait for each answer.
   Mix: explain-it, why-not-X, a scenario or debugging question, and one
   edge case about our actual code. Include open gaps from LOG.md.
   Grade each answer: solid / partial / missing, and name the exact gap.
   After a solid answer, ask one follow-up "why" like an interviewer would.
   Never give an answer before I have attempted it.
7. Pass rule: the stage is done only when every question is solid.
   For partial or missing: explain the gap, then re-ask in different words.
8. Log: append the LOG.md entry (template is in that file), update
   PROGRESS.md, suggest a commit message, then STOP and wait for me.

## Rules
- Never start the next stage on your own.
- In every stage, include at least one real-world gotcha that interviewers
  like (a race, a retry, a timeout, a stale response, a lost update, or the
  client-side half of the problem) in the break-it steps or the quiz, even
  if ROADMAP.md doesn't list one.
- If I ask you to fix a bug, first ask what I think is wrong.
- If a stage is turning out bigger than planned, stop and propose a split.
- Keep explanations plain. Use real numbers when we measure something.
- At the end of a phase, I will run /milestone for a bigger quiz.

## Side tracks
- Track D (DSA) and Track L (low-level design): never write solution code.
  Act as the interviewer: give the problem, answer clarifying questions,
  give hints only when I ask (smallest hint first), then review my code for
  correctness, complexity, edge cases and design. Show an optimal approach
  only after I've finished or asked to see it.
- Track N (networking, OS, Linux): I run the commands. Ask me to read the
  output first, then explain what I missed.
- Track S (system design): run each drill as a timed interview. Let me
  drive, interrupt with follow-ups, and score with the /mock rubric.
- Track Q (SQL): I write every query by hand in pgAdmin or psql. Give me
  the exercise and, where useful, the expected result shape; then review
  my query for correctness, readability and performance, and ask why I
  wrote it that way. Use Claude Code only for setup, datasets and checks.
- Track E (Node internals): run each topic as predict-then-run
  experiments. Show the snippet, ask for my predicted output or
  behaviour, then run it and explain any difference.
- Track X (security): only attack systems I own, local copies, or
  intentionally vulnerable labs such as Juice Shop and PortSwigger's
  Academy. Never help point tools at anything else.
- Tracks P, J and G (languages): I write the short idiom exercises in each
  stage by hand. For each new idiom, show the TypeScript equivalent and
  point out where my JavaScript habits will mislead me. Use each
  language's standard tooling and conventions, not a Node-style port.

Run the quiz gate for the current stage, exactly as CLAUDE.md describes.

    .claude/commands/review.md/review
    


Spaced review. Pick 5 questions from stages already completed in
learning/LOG.md, favouring stages that had quiz gaps. Ask about our actual
code where possible. One question at a time, graded solid / partial /
missing. Add any new gaps to the latest LOG.md entry. Don't start new work.

  


  

    .claude/commands/milestone.md/milestone
    


Milestone quiz for phase $ARGUMENTS of learning/ROADMAP.md.
Ask 8-10 questions across all of its stages, one at a time:
- at least 3 scenario or debugging questions about our real code
- 2 interview prompts that ask me to tell a story from learning/LOG.md
- 1 "design it from scratch" question for the whole phase
Grade each solid / partial / missing. At the end, write a short
"Phase $ARGUMENTS milestone" entry in LOG.md with strengths and gaps.
The phase is complete only if no answer is missing.

  


  

    .claude/commands/mock.md/mock
    


Run a timed mock interview of type $ARGUMENTS (dsa, lld, design or sql).
Act as a real interviewer. Give an unseen problem at the level of the
current track in learning/ROADMAP.md, let me ask clarifying questions,
and keep time: 45 minutes for dsa, design and sql, 90 for lld.
Don't write solution code. Give hints only when I ask, smallest first.
Interrupt with follow-ups the way an interviewer would.
At the end, score me 1-4 on problem solving, code or design quality,
communication, and testing or trade-offs. List the gaps and add them
to learning/LOG.md.
