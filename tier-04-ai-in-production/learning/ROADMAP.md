# Roadmap: Tier 4, AI in production

App: shop-assistant, continued from Tier 3 and made production-grade.

## Phase 19: Evals
Turning "it seems better" into numbers you can trust, run on every change.

### 19.1 Golden datasets
Goal: A reviewed set of test cases for every AI feature in the assistant.
Build:
- 50–100 cases each for Q&A, intent classification and tool use
- Synthetic cases generated by a model, then reviewed by you
- Expected outcomes recorded per case
Understand:
- Why evals start with good data
- Synthetic data and its blind spots
- Covering edge cases, not just typical ones
Break it:
- Generate cases without review and count the wrong labels
Quiz focus:
- Why must synthetic test data be reviewed by a person?
Done when: Each feature has a dataset you'd trust to judge it.

### 19.2 Code-graded evals
Goal: Automatic scores for everything that can be checked by code.
Build:
- An eval runner that scores classification accuracy, schema validity, correct tool calls and citation presence
- A report comparing two runs
Understand:
- Which checks need no model at all
- Why deterministic checks come first
Break it:
- Change the prompt and watch the scores move
Quiz focus:
- Which of your features can be graded without an LLM judge?
Done when: One command gives a score report for every feature.

### 19.3 LLM-as-judge
Goal: Open-ended answers graded by a model you've checked against your own judgement.
Build:
- Rubric-based judging for support answers
- Pairwise comparison between two versions
- Agreement measured between the judge and your own labels
Understand:
- Judge biases: position, length and self-preference
- Rubrics vs open-ended judging
- Why judges need calibration
Break it:
- Swap the order of two answers in pairwise judging and compare verdicts
Quiz focus:
- How do you know your judge is trustworthy?
- What is position bias, and how do you control for it?
Done when: Your judge agrees with you on a measured share of cases.

### 19.4 RAG evals
Goal: You can tell whether a bad answer came from retrieval or generation.
Build:
- Retrieval recall@k on questions with known sources
- Faithfulness checks that answers are supported by the retrieved text
- Answer relevance scores
Understand:
- Separating retrieval failures from generation failures
- Why faithfulness and correctness are different
Break it:
- Make chunking worse and see which metric drops
Quiz focus:
- Answers got worse after a change. How do you find which half of RAG broke?
Done when: Every RAG failure can be attributed to a stage.

### 19.5 Evals in CI and production
Goal: Regressions are caught before merging, and real usage feeds the dataset.
Build:
- A cost-limited eval subset that gates pull requests
- Thumbs up and down feedback captured in the app
- Sampling real conversations into the review queue
Understand:
- Offline vs online evaluation
- Keeping eval costs under control in CI
Break it:
- Open a pull request with a prompt change that lowers the score
Quiz focus:
- How do you keep a CI eval gate from costing a fortune?
Done when: No prompt or model change merges without passing evals.

Phase 19 milestone: 8–10 questions across Phase 19, including: your PM says the new prompt "feels better." How do you settle it?

## Phase 20: Benchmarks and model selection
Choosing models by evidence on your own task, not by leaderboard headlines.

### 20.1 Reading public benchmarks
Goal: You can explain what popular benchmarks measure and where they mislead.
Build:
- A short written comparison of knowledge, coding and agent benchmarks
- Notes on contamination and leaderboard caveats
Understand:
- What a benchmark score does and doesn't tell you
- Training-data contamination
- Why your task may behave differently
Break it:
- Take one benchmark claim and list three reasons it might not hold for your shop assistant
Quiz focus:
- A model tops a leaderboard. Why might it still be worse for you?
Done when: You can read any benchmark claim critically.

### 20.2 Your own benchmark
Goal: Several models compared on your eval set by quality, speed and cost.
Build:
- Three or more models run on your Tier 4 datasets
- A table of quality, time to first token, total latency and cost
- Repeated runs to measure variance
Understand:
- Why one run isn't enough
- Trading quality against latency and cost
Break it:
- Run once, then five times, and compare the spread
Quiz focus:
- How many runs do you need before trusting a difference between two models?
Done when: You have a model comparison table you'd show a manager.

### 20.3 Model routing
Goal: Each request goes to the cheapest model that handles it well.
Build:
- Routing by task: a small model for classification, a larger one for complex answers
- Escalation to a bigger model on low confidence
Understand:
- Routing by task vs by difficulty
- The cost savings and the quality risks
Break it:
- Route everything to the small model and measure the quality drop
Quiz focus:
- How would you cut AI costs by half without users noticing?
Done when: Routing cuts cost with no measurable quality loss.

### 20.4 Upgrading models safely
Goal: New model versions are adopted with evidence and can be rolled back.
Build:
- Pinned model versions
- Shadow testing a new model on copied traffic
- A switch and rollback plan
Understand:
- Why model upgrades can break working prompts
- Shadow testing vs A/B testing
Break it:
- Swap the model without running evals and find what broke
Quiz focus:
- A provider releases a new model version. Walk through adopting it.
Done when: Model changes go through the same safety process as code.

### 20.5 Reasoning models
Goal: Know when extended thinking is worth its cost.
Build:
- The same eval set run with thinking off, at a low budget and at a high budget
- Cost, latency and quality compared per task type
Understand:
- How reasoning models are trained with reinforcement learning on verifiable problems
- Why thinking helps with maths, code and planning but not with simple lookups
- Thinking budgets and what they cost
Break it:
- Turn on maximum thinking for intent classification and compare cost against quality
Quiz focus:
- When is a reasoning model the wrong choice?
- How would you decide a thinking budget for a feature?
Done when: Each feature uses extended thinking only where your evals show it pays off.

Phase 20 milestone: 6–8 questions across Phase 20, including: pick the model for a new feature, with the evidence you'd need.

## Phase 21: LLMOps
Running AI features like any other production system: traced, budgeted, cached and behind one gateway.

### 21.1 Tracing
Goal: Every AI answer can be explained from its trace.
Build:
- Traces recording prompt version, model, tokens, latency, tool calls and retrieved chunks
- A self-hosted LLM tracing tool or OpenTelemetry
Understand:
- What to capture for AI debugging
- Privacy concerns in AI traces
Break it:
- Debug a bad answer using only its trace
Quiz focus:
- A user reports a wrong answer from yesterday. What do you need to explain it?
Done when: Any answer can be reconstructed and explained.

### 21.2 Cost accounting and abuse
Goal: You know what AI costs per user and feature, and nobody can run up your bill.
Build:
- Token and rupee cost per user, tenant and feature
- Budgets with alerts
- Per-user rate limits on AI endpoints
Understand:
- Why AI endpoints are a cost attack surface
- Cost allocation for pricing decisions
Break it:
- Hammer the chat endpoint from a script
Quiz focus:
- Someone found your chatbot and is using it as a free LLM. How do you notice and stop it?
Done when: Cost is visible per user and capped.

### 21.3 Caching
Goal: Repeated questions are answered cheaply without wrong hits.
Build:
- An exact-match response cache
- A semantic cache with a similarity threshold
- Cache invalidation when documents change
Understand:
- Why semantic caching can return the wrong answer
- Picking a safe threshold
Break it:
- Find two different questions the semantic cache treats as the same
Quiz focus:
- When is a semantic cache too risky to use?
Done when: Cache hits are measured and wrong hits are rare and known.

### 21.4 An LLM gateway
Goal: Every model call in the system goes through one internal gateway.
Build:
- A gateway that hides providers behind one interface
- Central keys, retries, fallbacks across providers, logging and rate limits
Understand:
- The same idea as one API wrapper for all calls, applied to models
- Provider lock-in and how a gateway reduces it
Break it:
- Take the primary provider down and watch failover
Quiz focus:
- Why route all model calls through one place?
Done when: Switching or adding a provider touches one service.

### 21.5 Latency and AI UX
Goal: AI features feel fast even when the work is slow.
Build:
- Time to first token tracked per feature
- Streaming partial structured output
- Progress updates for multi-step agent tasks
Understand:
- Time to first token vs total time
- How progress updates change perceived speed
Break it:
- Measure first-token and total time for every feature and find the worst
Quiz focus:
- An agent task takes 40 seconds. How do you keep users from leaving?
Done when: Every feature shows something useful within a second or two.

Phase 21 milestone: 8–10 questions across Phase 21, including: your AI bill tripled this month. Walk through your investigation.

## Phase 22: AI security and safety
Attacking your own assistant the way real attackers do, then closing the gaps.

### 22.1 Indirect prompt injection
Goal: Instructions hidden in documents, reviews or tool results can't take control.
Build:
- Retrieved content and tool results clearly marked as data
- Separating what the model can read from what it can do
- Injection test cases planted in product descriptions
Understand:
- Direct vs indirect injection
- Why any text the model reads is an attack surface
Break it:
- Put instructions in a product description and ask the assistant about that product
Quiz focus:
- A seller hides instructions in their product description. What could happen, and what stops it?
Done when: Planted instructions don't change what the assistant does.

### 22.2 Data exfiltration
Goal: An injected instruction can't send private data out.
Build:
- Restrictions on links and images in responses
- Least-privilege tools
- A check for the dangerous combination: private data, untrusted content and a way to send data out
Understand:
- How a rendered image URL can leak data
- Why that three-part combination is the real danger
Break it:
- Make an injection that outputs a link containing order details
Quiz focus:
- How can a chatbot leak data just by showing an image?
Done when: No response can carry private data to an outside address.

### 22.3 PII and data handling
Goal: Personal data is minimized, redacted and deletable.
Build:
- PII redaction before logs and traces
- Retention limits for conversations
- User deletion that reaches traces and caches
Understand:
- What counts as personal data
- Provider data retention policies
Break it:
- Search your traces for a phone number
Quiz focus:
- A user asks you to delete everything about them. Where does AI-related data hide?
Done when: No personal data sits in logs or traces unredacted.

### 22.4 Guardrails and red-teaming
Goal: Unsafe inputs and outputs are caught, and you have a red-team report.
Build:
- Input and output checks for topic, toxicity and policy
- A refusal experience that still helps the user
- A red-team session against the OWASP Top 10 for LLM applications, with a written report
Understand:
- What guardrails catch and what they miss
- Jailbreak patterns
Break it:
- Run 30 red-team prompts and record the pass rate
Quiz focus:
- What are the top three risks for your assistant, and your mitigations?
Done when: You have a red-team report with fixes for every high finding.

Phase 22 milestone: 6–8 questions across Phase 22, including: a security team asks whether your AI assistant is safe to launch. Make your case.

## Phase 23: Multimodal and voice
Images, documents and speech as inputs, ending with a real-time voice assistant.

### 23.1 Search by photo
Goal: Customers find similar products by uploading a photo.
Build:
- Image understanding or image embeddings for products
- Photo upload with size limits and resizing
- Similarity search over product images
Understand:
- Image tokens and their cost
- Describing images vs embedding them
Break it:
- Upload a huge image and check the cost
Quiz focus:
- Why resize images before sending them to a model?
Done when: Photo search returns sensible matches at a known cost.

### 23.2 Document extraction
Goal: Invoices and GST bills become validated structured data.
Build:
- PDF and image extraction into a schema
- Validation and confidence per field
- A human review queue for low-confidence fields
Understand:
- Where extraction fails: scans, rotation, tables
- Validating extracted totals against line items
Break it:
- Feed a rotated scan and a multi-page invoice
Quiz focus:
- How do you catch an extraction that looks valid but is wrong?
Done when: Bad extractions reach a person, not the database.

### 23.3 Speech in and out
Goal: Users can ask by voice and hear the answer.
Build:
- Speech-to-text for voice questions
- Text-to-speech for answers
- Streaming both directions
Understand:
- Accuracy with accents, noise and Hinglish
- Streaming audio vs whole files
Break it:
- Send noisy audio and code-mixed speech
Quiz focus:
- Where does the delay come from in a voice reply?
Done when: Voice questions work for Indian English and Hinglish.

### 23.4 Real-time voice agent
Goal: A voice assistant that responds fast and handles interruptions.
Build:
- Audio streamed over WebSockets
- A latency budget across speech-to-text, the model and text-to-speech
- Interruption handling that cancels the reply in flight
Understand:
- Why voice needs sub-second responses
- Interruption as a cancellation problem, the same one from Tier 1
Break it:
- Interrupt the assistant mid-sentence
Quiz focus:
- The user talks over the assistant. What should happen in each part of the pipeline?
Done when: Replies start quickly and stop the moment the user speaks.

### 23.5 Voice in the browser
Goal: Voice input and output work in the browser with good permission and error handling.
Build:
- Microphone permission flow and errors
- Audio capture with the Web Audio API and streaming to the server
- Push-to-talk and interruption controls
Understand:
- Browser permission models
- Audio formats and sample rates
Break it:
- Deny microphone permission, then grant it later
Quiz focus:
- What can go wrong between pressing the mic button and audio reaching your server?
Done when: Voice works across the main browsers with clear handling of every permission state.

Phase 23 milestone: 6–8 questions across Phase 23, including: design a phone support agent for a delivery app.

Every prompt or model change is gated by evals in CI. You have a model comparison table, cost per user on a dashboard, a gateway with provider failover, a red-team report with fixes, and one multimodal feature live. Run a 15-question quiz across Phases 19–23, and turn five LOG.md entries into interview stories, including one where evals caught something you'd have shipped.
